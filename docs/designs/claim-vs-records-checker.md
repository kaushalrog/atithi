# Design: Claim-vs-records checker for action-taking voice agents

## Problem Statement

Voice agents that *take actions* (book, reschedule, record a lead) can tell a caller something was done when the business's records say otherwise. The agent says "you're booked for 4 PM" and the booking is missing, duplicated, sits in a different slot, or failed silently. The caller believes it. The business finds out when the customer shows up, or never finds out.

VoxAgent's own Phase 0 audit (`docs/AUDIT.md`) is the evidence. Every failure that would have hurt a client lived in system state, not in how the conversation sounded:
- concurrent double-booking (H2, reproduction R1)
- Sheet bookings invisible to availability (H3, R2)
- a conversion metric that counted failed bookings (M1, R3)
- phone and live calls that dropped tool calls from the call record (M2, R4)

The founder's existing checks, 10 scripted evals plus reading transcripts, missed all of them. Of these four, the checker below targets the three that show up in a single call's trace plus the records (R1, R2, R4). R3 is a dashboard aggregation bug, not a claim-vs-records mismatch. The checker does not detect it, and the fix belongs in the metrics code (M1, TODOS.md).

## Recommended Approach: A

### MVP scope (first release, committed)

The flow: a trace (neutral format) plus a records file → validated → 6 checks → evidence-linked findings and a task outcome → a saved run (one JSON file under `runs/`, local) → `compare` two run files (new / fixed / unchanged findings, printed and in the HTML report) → one static HTML report → pytest fixtures run in CI with no API key.

**Replay** means re-running the checks on a frozen trace. It answers "did my checker change, or my records change, alter the verdict?" It does **not** show the effect of a prompt change, because a prompt change needs a new conversation. To test a prompt change, the builder makes a new call by hand (terminal or test call), which produces a new trace, and then compares the two runs. That path uses the builder's own LLM quota and is outside the $0 guarantee. No synthetic caller is generated.

**After demand is validated (not in the first release):** checks 7 to 9 below, SQLite storage of runs, an HTML page comparing two runs side by side, the outside-format adapter (built once a builder names a platform), and the optional LLM judge.

### Trace format (neutral)

One JSON document per call. Validated with pydantic, rejected with a clear error if malformed.
- `call_id`, `started_at` and `ended_at` (ISO 8601 **with UTC offset**, required), `timezone` (IANA name; defaults to the business's configured timezone, else `Asia/Kolkata`).
- `turns`: ordered list of `{index, speaker: agent|caller, text, at}`.
- `actions`: ordered list of `{turn_index, at, type, name, args, ok, result}`.
  - `type` is one of `availability`, `book`, `lead`, `other`. Checks only reason about the type, never about a tool name.
  - `ok` is the normalised success flag.
- `records_as_of`: the timestamp the records snapshot represents (see Records).
- `records_snapshot` (optional): record rows embedded in the trace, in the records-file shape (see Records).

**Mapping.** Each source has a small mapping (YAML), with tool name → `type`, plus the success rule, e.g. `book_appointment: {type: book, ok_when: "result.status == 'confirmed'"}`. `ok_when` is a field-equality rule, never evaluated code. VoxAgent's mapping ships built in. An outside adapter is a converter from that platform's export into this format plus its mapping file.

### Records

**Input.** A records file (CSV or JSON) of bookings and leads: `booking_id` (optional), `phone`, `name`, `date`, `time`, `service`, `status`, `updated_at` (optional).

**Snapshot semantics.** Records are judged **as of call end**.
- VoxAgent writes `records_snapshot` into the trace at call end: **every confirmed row for that business on each date the call touched** (any date in an `availability` or `book` action's args or result), not just this caller's rows, **plus every lead row for the caller's normalised phone** (leads have no slot, so they are matched by phone alone). Checks 1 and 2 need other callers' rows, and check 1 needs the lead rows. The snapshot is the evidence, so later edits never change the verdict.
- **Precedence.** For the per-call checks (1, 2, 4 to 6), an embedded `records_snapshot` wins over a supplied records file. A supplied file is used for traces without a snapshot, such as outside exports. Check 3 (double booking) is a whole-records check: it runs on the supplied records file, which for VoxAgent is an export of `bookings.db` as of the run.
- An outside builder's export is usually taken later. Rows whose `updated_at` is after `ended_at` (a legitimate reschedule or cancellation) are not compared. They are reported as `unverifiable: changed after call`, which is neither a finding nor a pass.
- If `updated_at` is missing, the report says so once and the comparison proceeds.

**Matching a claim or action to a record row:**
1. Match by `booking_id` if the action result and the row both carry one.
2. Otherwise match by a composite key: the last 10 digits of the phone, the date, and the time normalised to HH:MM.
3. If there's no match, look for any row with the same normalised phone whose `updated_at` is after `ended_at`. If one exists, the booking was probably rescheduled or cancelled after the call, so the result is `unverifiable: changed after call`, citing that row. Only if there is no such row is the result "record missing".
4. More than one matching row → `ambiguous match`: listed with both rows as evidence, not counted as a pass or a failure.

**Time.** Relative dates ("tomorrow") and bare times ("4 PM") are resolved against `started_at` in the trace's `timezone`. Results are reproducible because both are in the trace.

### Checks

Each check is labelled **exact** (comparison of structured fields) or **heuristic** (a documented phrase or pattern matcher). Heuristic findings carry the label in every report. Each finding cites its evidence (turn index and text, action, record row or its absence).

MVP checks, in order of value:
1. **Record mismatch** (exact). A `book` or `lead` action has `ok=true`, but the matched record is missing or differs in date, time, phone or service.
2. **Slot not available.** This check has two parts, labelled separately:
   - **2a (exact):** a `book` action with `ok=true` targets a slot that no earlier `availability` result in the call contained, or one the records show as already confirmed for another caller. It compares only structured fields: action args, availability results and record rows. This targets R2 (Sheet bookings invisible to availability), where a booking landed on an already-taken slot.
   - **2b (heuristic):** an agent turn offers a date and time (using check 5's phrase normaliser) that no `availability` result in the call contained, even if nothing was booked.
3. **Double booking** (exact, across calls). Two confirmed rows share client, date and time in the records. This targets R1.
4. **Claim without action** (heuristic). An agent turn matches a booking-confirmation phrase list ("you're booked", "booking is confirmed", "see you on …"), but no `book` action with `ok=true` exists at or before that turn's index. **Window:** from the start of the call to the end of the claim's turn, which includes actions with the same `turn_index`, because some platforms log the action after the speech in that turn. This also targets R4 (tool calls missing from the record of the call).
5. **Spoken time differs** (heuristic). A date or time phrase in an agent turn, normalised ("4 PM" → 16:00, "tomorrow" → `started_at` date + 1 in `timezone`), differs from the args or result of the `book` action that the turn confirms.
6. **Incomplete task** (exact). The call has at least one `availability` or `book` action (the definition of "intent shown"), but no `book` or `lead` action with `ok=true`. The same check also fails a successful `book` or `lead` whose args lack a required field (name, phone, date and time for a booking; phone for a lead).

**Task outcome** for each call, derived from the actions only:
- `booked`: there is a `book` action with `ok=true` and a matched record.
- `booked_unverified`: there is a `book` action with `ok=true`, but the record is missing, ambiguous or unverifiable.
- `lead_saved`: there is no booking, but there is a `lead` action with `ok=true`.
- `incomplete`: intent was shown, with neither of the above.
- `no_intent`: there were no `availability` or `book` actions.

Post-validation checks (heuristic, deferred because each needs a phrase rule that we can't tune without real logs):
7. **Unsupported business claim.** A currency amount (₹/Rs/rupees + number) is stated that doesn't match any price in the business config. Free-text policy claims stay out of scope.
8. **Repeated question.** The agent asked for the same required field (detected by field keyword: name, phone, date, time) 3 or more times.
9. **Correction not applied.** A caller turn matches a correction pattern ("no, it's …", "actually …") followed by a phone, date or time value, and the final `book` action uses the earlier value.

### Input safety and personal data

- Transcripts are untrusted. Instructions inside them are data, never executed. Payload size is bounded (traces ≤ 1 MB, ≤ 500 turns), and malformed input is rejected with a clear error.
- **HTML report:** every trace-derived string is passed through `html.escape`. There's no raw insertion and no external scripts, fonts or styles, and a restrictive Content-Security-Policy meta tag is set. An adversarial fixture (a transcript containing `<script>`, `<img onerror>` and an "ignore previous instructions" line) must render as inert text. A test asserts this.
- **Personal data:** traces and records hold callers' names and phone numbers.
  - Everything runs locally; nothing is uploaded.
  - Reports and run files mask phones to the last 4 digits by default.
  - A `redact` command replaces names with tokens and phones with a consistent keyed hash, so matching still works before a builder shares anything.
  - Shared builder data is used only with their consent. It is kept outside the repo, never committed, and deleted within 30 days or when the test ends. Repo fixtures are synthetic.

### VoxAgent event log (step zero)

- During a call, events are appended to an in-memory list on the call object only, with no disk I/O, YAML parsing or client construction on the caller-to-answer path.
- At call end, `storage.py` writes the trace once.
- A failure to build or write the trace is caught and logged and never raised into the call. The call record is kept even if the trace isn't.
- `bench.py` gains an event-append measurement, so a regression in the hot path shows up.
- This closes audit gap M2, and it removes the substring-based conversion metric behind M1 once the dashboard reads action outcomes.

## Success Criteria

**Product (measured on fixtures; numbers are targets, not results):**
- **Recall** = detected injected faults / injected faults, overall ≥ 90%, with every MVP check catching its own faults. Measured on ≥ 10 fault-injected traces, each carrying one labelled fault, with at least one per MVP check:
  - R1 double booking (check 3)
  - R2 a booking on an already-confirmed slot (check 2a)
  - R4 a confirmed booking with no logged action (check 4)
  - a successful tool with a missing record (check 1)
  - a spoken time that contradicts the booking (check 5)
  - an incomplete task (check 6)
  - a missing required field (check 6)
  - plus 3 more variants of checks 1, 4 and 5
- **False positives:** at most 1 across ≥ 20 clean traces. The "correct call" brief case belongs here.
- **Input handling** (pass/fail, not recall): malformed traces are rejected with a clear error; the adversarial trace is processed without following its instructions, and its report renders inertly.
- **Brief cases deferred** with checks 7 to 9: unsupported policy claim, repeated questions, correction not applied. Their fixtures land with those checks.
- **Cost:** $0 in API costs to run the checks and the tests.
- **Onboarding:** a new user goes from `git clone` to a report on the sample case in ≤ 10 minutes, using documented steps.
- **Replay and compare:** a frozen trace re-runs after a checker change, and `compare` reports new and fixed findings.

**Demand (the real test):**
- Contact at least 10 builders by day 3, aiming for at least 5 substantive replies, i.e. an answer to the question, not "cool".
- **Day 10 checkpoint.** Evaluate these in order; the first that applies is the answer:
  1. **Too few replies:** fewer than 5 substantive replies. Spend 7 more days on outreach only (new channels, no new checks), then re-run this checkpoint once. If there are still fewer than 5, the result is **kill**: a market that won't answer one question won't adopt a tool.
  2. **Kill or rethink:** 0 of the replies report a claim-vs-records failure in the last month. Stop building and re-run office hours.
  If at least 1 builder reports a failure, the checkpoint opens a **run window of 4 days** from the day it was passed (day 10, or day 17 on the extension path). Branches 3 and 4 are decided on the last day of that window (day 14, or day 21):
  3. **Pain, and someone runs it:** at least 1 builder has run the checker on their own logs within the run window. This is **success**: keep building, starting with that builder's adapter.
  4. **Pain, but no one runs it in the window:** the pain is real, but the tool isn't the answer yet, or the setup cost is too high. Ask each builder who reported pain what stopped them, fix only that blocker, and open one more 7-day run window. A run in that window counts as success. If there's still no run, re-run office hours on the wedge (e.g. a service where they send logs and get a report) before writing more checks. No further extensions, so the decision lands by day 21, or day 28 on the extension path.

### R3-1 — completeness (blocking)

**Problem**

> The snapshot holds only confirmed booking rows for the dates the call touched, but check 1 also covers `lead` actions, and leads have no confirmed status or slot date. The new precedence rule says an embedded snapshot wins over a supplied records file for check 1. So on every VoxAgent trace, a successful `lead` action finds no row in the snapshot and is reported as 'record missing', and the task outcome logic gets no lead row either. Every saved lead becomes a false positive, which breaks the 1-in-20 false-positive target for clean traces that end with a lead.

**Remedy**

> Add the lead rows written during the call (or every lead row for the caller's normalised phone) to `records_snapshot`. Alternatively, state that lead matching for check 1 falls back to the supplied records file when the snapshot has no lead rows.

### R3-2 — clarity (blocking)

**Problem**

> The extension branch re-runs the checkpoint around day 17, but branches 3 and 4 still use fixed deadlines: 'run the checker ... by day 14' and 're-check at day 21'. On the extension path, the day-14 deadline has already passed when the re-run happens, so branch 3 (success) can never apply and every extended outcome with pain falls into branch 4.
